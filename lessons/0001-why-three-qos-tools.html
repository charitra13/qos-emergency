QoS emergency project · 4 minute lesson

Why have a simulation, a live demo, and a dashboard?

They answer different questions about one idea: when a network link is overloaded, can emergency packets still get through quickly and reliably?

The short answer: simulation helps you explore many controlled “what ifs”; the live demo checks the code with real packets and sockets; the dashboard helps people compare and understand results. Together they make the claim easier to test, trust, and explain.

Start with the problem

Imagine an emergency alarm, a voice call, video, and a large file all sharing a narrow network link. If the link is full, packets must wait or be dropped. A basic FIFO queue treats them alike. QoS (Quality of Service) gives important traffic preferential treatment, while trying to keep lower-priority traffic usable too.

“Why is this needed?” Because normal conditions can hide the problem. The project’s own notes say FIFO can meet the targets at ordinary load; congestion, outages, false emergency markings, and overload reveal whether prioritization actually helps.

Three tools, three jobs

1 · Simulation = exploreChange the scenario and compare schedulers under repeatable conditions. Useful for many cases: congestion, link failure, spoofing, starvation, or a load sweep.
2 · Live demo = check realityReal UDP senders, a software QoS router, and a receiver exchange packets on the machine. This checks socket handling and queue behavior outside the simulator.
3 · Dashboard = understandChoose a scenario and see scheduler results as SLA verdicts, charts, and an emergency-delay timeline. It presents simulation output; it is not a separate network experiment.
View What it answers What to look at Limit
Simulation “What happens if we change the traffic or failure?” Compare FIFO, PQ, WFQ, DRR, and EPS on p99 delay, loss, throughput, and SLA. It follows the simulator’s model; it cannot prove behavior of every real OS or network.
Live demo “Does the implementation work with actual packets moving through it?” Emergency/voice delay and loss during overload; compare schedulers, optionally add a spoofed flow. It runs on loopback with a software rate limiter, so results vary with machine timing and are not a field deployment.
Dashboard “Can I see the comparison and explain the result quickly?” PASS/FAIL by class, p99 delay, loss, throughput, and emergency delay over time. It runs the simulator through a web page; a chart is only as good as the data and model behind it.

Why not use just one?

A simulation is controlled and repeatable, so you can test more edge cases cheaply. A live demo uses real operating-system networking, so it can catch issues the model leaves out. A dashboard makes the evidence legible to someone who does not want to read raw terminal output. These are complementary checks, not three independent proofs.

There is also an optional fourth layer: Mininet emulation. It uses Linux network namespaces and virtual links to run real networking code in a virtual topology. In this project, it is an extra, Linux-only experiment; the instructions say it was not run in the authoring environment. A useful way to present the project

Tell the story in this order: problem → controlled evidence → implementation check → readable comparison. For example, show TC2 congestion in the dashboard, explain that FIFO’s emergency p99 delay rises while priority schedulers keep it low, then run the live demo to show the same broad behavior with real UDP traffic. Be precise that the live demo is local software networking, not a real disaster network.
